# S1.4.2.1 — Auditoría del modelo actual de identidad, roles y autorización

## 1. Propósito

Documentar el estado **AS-IS** del modelo de identidad, autenticación, roles y autorización sobre el baseline funcional cerrado en **S1.4.1**, antes de introducir cambios funcionales.

Esta subfase es exclusivamente diagnóstica. Durante la auditoría no se modificó la implementación del repositorio.

## 3. Alcance

## 4. Modelo de identidad AS-IS

### User

`App\Models\User` extiende `Authenticatable`, utiliza `HasFactory` y `Notifiable`, y admite `name`, apellidos, CURP, email, celular, password, `activo` y `role_id`.

Casts relevantes:

- `email_verified_at` → `datetime`
- `password` → `hashed`
- `activo` → `boolean`

Relación:

```php
public function role(): BelongsTo
{
    return $this->belongsTo(Role::class);
}
```

### Role

`App\Models\Role` conserva una estructura mínima con `name` y la relación:

```php
public function users(): HasMany
{
    return $this->hasMany(User::class);
}
```

El modelo resultante es:

```text
Role 1 ───────── N User
                   └── role_id nullable
```

## 5. Esquema de base de datos

`roles` contiene `id`, `name`, timestamps y un índice UNIQUE sobre `name`.

`users` contiene 14 columnas: `id`, `name`, apellidos, `curp`, `email`, `celular`, `email_verified_at`, `password`, `activo`, `role_id`, `remember_token` y timestamps.

Restricciones relevantes:

- `curp`, `email` y `celular` tienen unicidad;
- `curp` y `celular` son nullable;
- `activo` tiene valor predeterminado `true`;
- `role_id` es nullable;
- FK `users.role_id → roles.id`;
- eliminación del rol: `ON DELETE SET NULL`.

La migración crea también `password_reset_tokens` con `email` como clave primaria, `token` y `created_at`.

## 6. Roles actuales

`RolesSeeder` crea mediante `firstOrCreate()`:

```text
Administrador
Usuario
```

`DatabaseSeeder` ejecuta únicamente `RolesSeeder`.

## 7. Autenticación

`config/auth.php` utiliza un único guard `web` basado en sesión y el provider Eloquent `users`, asociado a `App\Models\User`.

Se conservan:

- login y logout;
- recuperación/restablecimiento de contraseña;
- actualización y confirmación de contraseña;
- verificación de email;
- edición de perfil;
- rate limiting.

El registro público permanece eliminado intencionalmente.

## 8. Hallazgo prioritario: `activo`

El atributo `activo` existe en modelo y base de datos, pero el login ejecuta:

```php
Auth::attempt(
    $this->only('email', 'password'),
    $this->boolean('remember')
);
```

Por tanto, `activo` no interviene actualmente en la autenticación.

```text
activo = true  + credenciales válidas → autenticación posible
activo = false + credenciales válidas → autenticación también posible
```

Actualmente `activo` es información persistida, pero no un control efectivo de acceso.

**Riesgo: ALTO.**

## 9. Rutas y perfil

`/dashboard` y las operaciones de perfil están protegidas mediante `auth`.

Las rutas de autenticación utilizan `guest`/`auth` y mantienen los controles de firma y throttling correspondientes.

No existe diferenciación de acceso por rol.

`ProfileUpdateRequest` valida únicamente `name` y `email`, por lo que ese flujo no permite modificar `role_id`, `activo`, CURP ni celular.

La eliminación de cuenta exige contraseña actual.

## 10. Estado de autorización

La búsqueda transversal no evidenció una capa de autorización de negocio implementada.

- `bootstrap/app.php`: sin aliases de middleware personalizados.
- Middleware de usuario activo: no existe.
- Middleware por rol: no existe.
- Gates: no evidenciados.
- Policies: no evidenciadas.
- Catálogo de permisos: no existe.
- Relaciones rol-permiso: no existen.
- RBAC completo: no implementado.

`role_id` permite conocer el rol, pero no autoriza acciones por sí mismo.

## 11. Dependencias

`composer.json` no evidencia un paquete especializado de RBAC/ACL. No se identificó infraestructura como Spatie Laravel Permission, Passport, Sanctum, Fortify o Jetstream.

Laravel Breeze permanece como dependencia de desarrollo asociada a la base de autenticación.

No existe, por tanto, una segunda arquitectura de autorización heredada que deba conservarse o desmontarse.

## 12. Factory y pruebas

`UserFactory` genera nombre, email, verificación, password y `remember_token`; no asigna explícitamente `role_id` ni `activo`.

La suite cubre autenticación, contraseñas, verificación, dashboard, perfil y ERP Core, pero no existe cobertura específica evidenciada para:

- usuario activo/inactivo;
- asignación de roles;
- autorización por rol;
- respuestas 403 por autorización;
- Gates;
- Policies;
- middleware de autorización.

## 15. Separación conceptual

```text
IDENTIDAD
└── ¿Quién es el usuario?
    └── User

AUTENTICACIÓN
└── ¿Puede demostrar quién es?
    └── email + password + sesión

AUTORIZACIÓN
└── ¿Qué puede hacer?
    └── rol + capacidades + Gates/Policies/middleware
```

La autenticación existente no debe reconstruirse innecesariamente. La capa de autorización debe construirse sobre ella.

## 16. Principios derivados para el diseño TO-BE

1. `activo` deberá convertirse en un control real de acceso. La estrategia para sesiones ya abiertas deberá definirse explícitamente.
2. Los nombres de roles no deben dispersarse mediante comparaciones de cadenas por controladores, vistas y módulos.
3. Autenticación y autorización deben permanecer separadas.
4. No se incorporará automáticamente un modelo complejo de permisos persistidos ni una dependencia RBAC externa.
5. La autorización deberá ser reutilizable por los módulos ERP posteriores.

## 18. Riesgos identificados

### R-01 — Usuario inactivo puede autenticarse
**Prioridad: alta.** `activo` no interviene en `Auth::attempt()`.

### R-02 — Rol sin efecto de autorización
**Prioridad: alta.** `role_id` se almacena, pero no existe una capa que lo convierta en decisiones de acceso.

### R-03 — Ausencia de pruebas de autorización
**Prioridad: alta.** Una implementación posterior podría introducir regresiones sin cobertura específica.

### R-04 — Dispersión futura de lógica de roles
**Prioridad: media.** Comparar nombres de roles directamente en cada módulo generaría acoplamiento y deuda técnica.

### R-05 — Factory incompleta
**Prioridad: media.** La factory no proporciona estados explícitos para roles o activación.

## 19. Decisiones fuera del alcance de esta auditoría

S1.4.2.1 no decide todavía:

- implementación exacta del control de usuario activo;
- mecanismo definitivo de autorización por rol;
- catálogo final de capacidades;
- Gates concretos;
- Policies necesarias;
- tratamiento definitivo de sesiones abiertas al desactivar usuarios;
- obligatoriedad futura de `role_id`;
- permisos dinámicos;
- incorporación futura de un paquete RBAC.

Estas decisiones corresponden al diseño TO-BE posterior.
