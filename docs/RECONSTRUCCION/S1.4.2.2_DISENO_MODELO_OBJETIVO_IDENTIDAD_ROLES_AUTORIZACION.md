# S1.4.2.2 — Diseño del modelo objetivo de identidad, roles y autorización

## 1. Propósito

Definir el modelo **TO-BE** de identidad, estado de cuenta, roles y autorización antes de modificar la implementación.

Esta subfase consolida las decisiones arquitectónicas derivadas de la auditoría **S1.4.2.1** y establece el contrato que deberá respetar la fase posterior de implementación.

Durante S1.4.2.2 no se implementan cambios funcionales.

# 4. S1.4.2.2.A — Principios y reglas de autorización

## 4.1 Separación de responsabilidades

El sistema distinguirá explícitamente:

```text
IDENTIDAD
└── ¿Quién es el usuario?
    └── User

AUTENTICACIÓN
└── ¿Puede demostrar quién es?
    └── email + password + sesión

ESTADO
└── ¿La cuenta puede utilizar el sistema?
    └── activo

AUTORIZACIÓN
└── ¿Qué puede hacer?
    └── rol + capacidades + Gate/Policy/can
```

El middleware `auth` continuará dedicado a autenticación.

La autorización no se implementará mediante lógica de roles incrustada en `auth`.

## 4.2 `activo` como control efectivo

La semántica objetivo será:

```text
activo = true
└── puede autenticarse si sus credenciales son válidas
└── puede conservar acceso sujeto a autorización

activo = false
└── no puede iniciar una nueva sesión
└── no debe conservar acceso funcional con una sesión previa
```

## 4.3 Un rol principal por usuario

Se conserva:

```text
Role 1 ───────── N User
                   └── role_id
```

No se introducirán múltiples roles por usuario en esta fase.

## 4.4 Autorización mediante capacidades

Los módulos no deberán depender directamente del nombre textual o ID del rol.

Se evitarán patrones como:

```php
if ($user->role_id === 1) {
    // ...
}
```

y:

```php
if ($user->role?->name === 'Administrador') {
    // ...
}
```

dispersos por la aplicación.

El acceso funcional se expresará mediante capacidades.

Ejemplo conceptual:

```php
$user->can('users.update');
```

## 4.5 Laravel nativo como base

La arquitectura utilizará inicialmente los mecanismos nativos de Laravel:

```text
Role
  ↓
capacidades
  ↓
Gate / Policy
  ↓
middleware can
  ↓
Controller / módulo
```

No se incorpora en esta etapa un paquete RBAC externo ni tablas de permisos dinámicos.

## 4.6 Default deny

La política será:

```text
sin regla explícita de autorización
→ DENEGAR
```

La ausencia de una capacidad nunca deberá convertirse en autorización implícita.

# 5. S1.4.2.2.B — Modelo objetivo User / Role

## 5.1 User

`User` seguirá siendo la entidad autenticable principal.

Responsabilidades:

```text
User
├── identidad
├── autenticación
├── estado
│   └── activo
└── autorización base
    └── role_id
```

El modelo deberá poder ofrecer primitivas de dominio equivalentes a:

```text
isActive()
hasRole()
hasRole(...)
isAdministrator()
```

Los nombres definitivos de métodos se fijarán durante implementación, respetando estas responsabilidades.

`User` no deberá acumular permisos específicos de módulos.

## 5.2 Role

`Role` continuará siendo el catálogo persistido de roles.

Responsabilidades:

```text
Role
├── id
├── name
└── users()
```

No se convertirá en esta fase en un sistema persistido completo de permisos.

## 5.3 `role_id`

Se conserva `role_id` como nullable.

Semántica:

```text
role_id válido
→ usuario asociado al rol correspondiente

role_id = null
→ usuario sin rol
→ cero capacidades protegidas
```

`role_id = null` no significará implícitamente `Usuario`.

## 5.4 Identificadores canónicos de roles

Los roles no se autorizarán por ID de base de datos.

Se adopta como diseño objetivo un enum de dominio:

```php
enum RoleName: string
{
    case ADMINISTRATOR = 'Administrador';
    case USER = 'Usuario';
}
```

El enum no sustituye a la tabla `roles`; centraliza los nombres canónicos utilizados por la aplicación.

Arquitectura:

```text
RoleName
   │
   ▼
roles.name
   │
   ▼
users.role_id
```

## 5.5 Administrador

El usuario podrá responder conceptualmente:

```php
$user->isAdministrator();
```

La comparación con el identificador canónico deberá permanecer centralizada y no repetirse en módulos, controladores o vistas.

# 6. S1.4.2.2.C — Estado activo y sesiones

## 6.1 Dos controles distintos

El diseño debe resolver:

```text
A. Usuario inactivo intenta iniciar sesión
→ LOGIN DENEGADO

B. Usuario ya autenticado es desactivado
→ PIERDE ACCESO EN SU SIGUIENTE PETICIÓN PROTEGIDA
```

Agregar `activo` al login resuelve A, pero no resuelve por sí solo B.

## 6.2 Login

Conceptualmente, la autenticación deberá exigir:

```text
email correcto
+
password correcto
+
activo = true
```

Un usuario inactivo no deberá crear una nueva sesión válida.

## 6.3 Sesión existente

El flujo objetivo será:

```text
REQUEST
   │
   ▼
auth
   │
   ▼
active-user
   │
   ├── activo = false
   │      ├── logout
   │      ├── invalidar sesión
   │      ├── regenerar token CSRF
   │      └── redirigir a login
   │
   ▼
autorización
```

El control de estado se ejecutará después de autenticación y antes de autorización funcional.

## 6.4 Inactivo frente a no autorizado

```text
INACTIVO
→ deja de conservar acceso al sistema

ACTIVO SIN CAPACIDAD
→ conserva sesión
→ recibe 403 en la acción protegida
```

## 6.5 Desactivación

Desactivar no significa eliminar.

```text
activo = false
≠
DELETE user
```

La desactivación tampoco modificará automáticamente `role_id`.

Esto conserva identidad, relaciones, trazabilidad e historial.

## 6.6 Reactivación

Al cambiar:

```text
activo: false → true
```

el usuario conservará rol y credenciales y podrá volver a autenticarse normalmente.

## 6.7 Sesiones simultáneas

Esta fase no exige revocación instantánea de todas las sesiones remotas.

El contrato mínimo será:

```text
usuario desactivado
→ ninguna sesión existente podrá seguir accediendo
  después de su siguiente request protegido
```

Una futura revocación global inmediata deberá diseñarse como capacidad adicional si se requiere.

# 7. S1.4.2.2.D — Gates / Policies / Middleware

## 7.1 Orden canónico

```text
REQUEST
   ↓
auth
   ↓
active-user
   ↓
can / Gate / Policy
   ↓
Controller
```

## 7.2 Middleware `auth`

Responsabilidad exclusiva:

```text
¿Existe una sesión autenticada?
```

No deberá decidir estado, rol ni permisos.

## 7.3 Middleware `active-user`

Responsabilidad exclusiva:

```text
¿La cuenta autenticada continúa activa?
```

No comprobará roles ni capacidades.

## 7.4 Middleware `can`

Será el mecanismo principal para proteger endpoints mediante capacidades.

Ejemplo conceptual:

```php
Route::get('/usuarios', ...)
    ->middleware('can:users.view');
```

No se adoptarán middleware como `role:Administrador` o `admin-only` como estrategia principal.

## 7.5 Gates

Los Gates resolverán capacidades globales que no dependan de una instancia concreta.

Nomenclatura:

```text
<recurso>.<acción>
```

Ejemplos:

```text
users.view
users.create
users.update
users.deactivate

roles.view
roles.assign

organization.view
organization.manage
```

## 7.6 Policies

Las Policies se utilizarán cuando la autorización dependa de una instancia concreta.

Regla:

```text
¿depende de un recurso específico?

NO
→ Gate

SÍ
→ Policy
```

No se crearán Policies vacías o prematuras únicamente porque exista un modelo.

## 7.7 Administrador global

El Administrador activo dispondrá de bypass centralizado de autorización, conceptualmente equivalente a un `Gate::before()`.

No se repetirán excepciones administrativas en cada Gate, Policy o controlador.

El bypass nunca deberá convertir a un Administrador inactivo en usuario válido.

## 7.8 Usuario sin rol

```text
autenticado = sí
activo = sí
role_id = null
```

podrá conservar una sesión válida, pero cualquier capacidad protegida deberá ser denegada.

## 7.9 Rol Usuario

`Usuario` no significará “cualquier usuario que no sea administrador”.

Recibirá únicamente capacidades expresamente definidas.

## 7.10 Vistas

Blade podrá utilizar `@can` para presentación.

Sin embargo:

```text
botón oculto
≠
endpoint protegido
```

Toda operación sensible deberá estar autorizada en servidor.

## 7.11 Reutilización

La arquitectura deberá permitir reutilizar la autorización desde futuros puntos de entrada:

```text
Web ─────┐
API ─────┼──→ Gate / Policy
Job ─────┤
CLI ─────┘
```

# 8. S1.4.2.2.E — Matriz de acceso y criterios de prueba

## 8.1 Matriz principal

| Escenario | Autenticado | Activo | Rol | Capacidad | Resultado |
|---|---:|---:|---|---:|---|
| Guest en ruta protegida | No | — | — | — | Login |
| Usuario activo con capacidad | Sí | Sí | Usuario | Sí | Permitido |
| Usuario activo sin capacidad | Sí | Sí | Usuario | No | 403 |
| Administrador activo | Sí | Sí | Administrador | Bypass | Permitido |
| Usuario activo sin rol | Sí | Sí | `null` | No | 403 |
| Usuario inactivo intenta login | No | No | cualquiera | — | Rechazado |
| Usuario desactivado con sesión | Sí inicialmente | No | cualquiera | — | Logout + login |
| Usuario reactivado | No | Sí | conserva rol | según rol | Login permitido |
| Usuario sin rol en ruta sin capacidad | Sí | Sí | `null` | no requerida | Permitido |

## 8.2 Estados HTTP/flujo

```text
NO AUTENTICADO
→ login

AUTENTICADO + INACTIVO
→ logout
→ invalidación
→ login

AUTENTICADO + ACTIVO + SIN CAPACIDAD
→ 403

AUTENTICADO + ACTIVO + CAPACIDAD
→ permitir
```

## 8.3 Casos mínimos de prueba

| ID | Prueba | Resultado esperado |
|---|---|---|
| T01 | Login usuario activo | Permitido |
| T02 | Login usuario inactivo | Rechazado |
| T03 | Sesión activa + posterior desactivación | Logout en siguiente request |
| T04 | Reactivación | Login nuevamente permitido |
| T05 | Administrador activo | Bypass de capacidad |
| T06 | Administrador inactivo | Acceso bloqueado |
| T07 | Usuario con capacidad | Permitido |
| T08 | Usuario sin capacidad | 403 |
| T09 | Usuario sin rol | 403 en acción protegida |
| T10 | Usuario sin rol | Acceso a ruta solo `auth`/`active` |
| T11 | Desactivar usuario | Conserva `role_id` |
| T12 | Reactivar usuario | Conserva `role_id` |
| T13 | Capacidad desconocida/no concedida | Denegada |
| T14 | Guest en ruta protegida | Login |
| T15 | UI con `@can` | Acción oculta si no autorizado |
| T16 | Endpoint de UI oculta | Continúa protegido |
| T17 | Relación User→Role | Consistente |
| T18 | Rol eliminado con `SET NULL` | Usuario permanece sin rol |

## 8.4 Factory

La factory deberá facilitar estados semánticos equivalentes a:

```text
active
inactive
administrator
withRole(...)
withoutRole
```

Las pruebas no dependerán de IDs concretos ni de datos manuales de la base local.

## 8.5 Regresión

La suite completa deberá ejecutarse después de implementar autorización.

Baseline previo:

```text
61 passed
119 assertions
```

La implementación solo podrá aceptarse si las pruebas históricas y las nuevas pruebas permanecen en PASS.

# 9. S1.4.2.2.F — Cierre del diseño TO-BE

## 9.1 Arquitectura consolidada

```text
                        REQUEST
                           │
                           ▼
                         auth
                           │
                           ▼
                    active-user
                           │
                           ▼
                  autorización Laravel
                           │
              ┌────────────┼────────────┐
              │            │            │
              ▼            ▼            ▼
            Gate         Policy       can
              │            │            │
              └────────────┼────────────┘
                           ▼
                      Controller
                           │
                           ▼
                     Dominio / ERP
```

Modelo:

```text
User
├── identidad
├── autenticación
├── activo
├── role_id
├── role()
├── isActive()
├── hasRole(...)
└── isAdministrator()

Role
├── id
├── name
└── users()

RoleName
├── ADMINISTRATOR
└── USER
```

## 9.2 Decisiones normativas finales

```text
D-F01  User continúa como entidad autenticable principal.
D-F02  Role continúa como catálogo persistido.
D-F03  Cada usuario tendrá como máximo un rol principal.
D-F04  role_id continuará nullable.
D-F05  role_id = null no implica el rol Usuario.
D-F06  No se autorizará mediante IDs de roles.
D-F07  Los nombres canónicos de roles estarán centralizados.
D-F08  Se adopta como diseño objetivo un enum RoleName.
D-F09  activo será control efectivo de acceso.
D-F10  Un usuario inactivo no podrá iniciar sesión.
D-F11  Un usuario desactivado perderá acceso en su siguiente request protegido.
D-F12  El middleware de estado será independiente de auth y autorización.
D-F13  El orden será auth → active-user → autorización.
D-F14  Gates resolverán capacidades globales.
D-F15  Policies resolverán acciones sobre recursos concretos.
D-F16  can será el mecanismo principal de autorización de endpoints.
D-F17  Las capacidades utilizarán nomenclatura recurso.acción.
D-F18  La autorización será deny-by-default.
D-F19  Administrador tendrá bypass global centralizado.
D-F20  Administrador inactivo no tendrá acceso.
D-F21  Usuario activo sin rol tendrá cero capacidades protegidas.
D-F22  No se implementarán todavía permisos persistidos en DB.
D-F23  No se incorporará todavía un paquete RBAC externo.
D-F24  Los tests no dependerán de IDs concretos de roles.
D-F25  La factory soportará estados semánticos de rol y activación.
D-F26  Toda autorización nueva tendrá cobertura automatizada.
D-F27  La suite previa deberá permanecer sin regresiones.
```

## 9.3 Patrones explícitamente descartados

No se utilizarán como arquitectura principal:

```text
role_id === 1
role_id === 2

comparaciones de nombres de roles dispersas

middleware role:Administrador

middleware admin-only

permisos hardcodeados en controladores

seguridad basada exclusivamente en Blade/@can
```
