# S1.3.3 --- Reconstrucción limpia de identidad y acceso

Reconstruir la capa mínima de identidad y acceso después del retiro del
dominio heredado, dejando `users` y `roles` desacoplados de región,
territorio, ruta y demás conceptos anteriores.

Esta subfase forma parte de **S1 --- Saneamiento del repositorio**.

## 3. Eliminación de subroles

Se eliminó la migración:

`2025_09_25_191421_create_subroles_table.php`

### Decisión

La reconstrucción inicial no utilizará una jerarquía rígida de
`rol/subrol`.

Si posteriormente se necesita autorización más granular, deberá
evaluarse un modelo explícito de permisos o capacidades.

------------------------------------------------------------------------

## 4. Reordenamiento de migraciones

Las migraciones principales fueron reorganizadas para expresar
directamente el esquema objetivo.

Orden resultante:

1.  `0001_01_01_000000_create_roles_table.php`
2.  `0001_01_01_000001_create_users_table.php`
3.  `0001_01_01_000002_create_cache_table.php`
4.  `0001_01_01_000003_create_jobs_table.php`

También permanece:

`MIGRATION_NOTES.md`

### Razón

`users.role_id` depende de `roles`, por lo que la tabla `roles` debe
existir antes de crear la FK de `users`.

------------------------------------------------------------------------

## 5. Reconstrucción de roles

La tabla `roles` se redujo a una estructura mínima:

-   `id`
-   `name`
-   timestamps

`name` es único.

### Modelo

La relación prevista es:

`Role -> hasMany Users`

------------------------------------------------------------------------

## 6. Reconstrucción de users

La nueva tabla `users` conserva atributos propios de identidad,
autenticación y estado de cuenta.

### Campos conservados

-   `id`
-   `name`
-   `apellido_paterno`
-   `apellido_materno`
-   `curp`
-   `email`
-   `celular`
-   `email_verified_at`
-   `password`
-   `activo`
-   `role_id`
-   `remember_token`
-   timestamps

### Campos retirados

Se eliminaron del núcleo de `users`:

-   `estado_id`
-   `municipio_id`
-   `region_id`
-   `territorio_id`
-   `ruta`

### Decisión arquitectónica

La identidad de un usuario no debe concentrar relaciones pertenecientes
a módulos geográficos, organizacionales o de negocio.

Si esos datos vuelven a ser necesarios, deberán modelarse en el contexto
correspondiente.

------------------------------------------------------------------------

## 13. Resultado arquitectónico

La capa de identidad queda orientada a:

``` text
Role
 └── User
      ├── identidad
      ├── autenticación
      └── estado de cuenta
```

Los conceptos de negocio, organización y ubicación deberán residir fuera
del núcleo de autenticación.
