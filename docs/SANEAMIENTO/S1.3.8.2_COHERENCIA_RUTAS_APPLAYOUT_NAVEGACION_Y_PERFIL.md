# S1.3.8.2 --- Coherencia de Rutas, AppLayout, Navegación y Perfil

## 1. Objetivo

Validar y unificar la arquitectura visual base de Laravel después del
saneamiento de rutas y vistas, eliminando la coexistencia de mecanismos
incompatibles de layout y asegurando coherencia entre:

-   `AppLayout.php`;
-   `layouts/app.blade.php`;
-   `layouts/navigation.blade.php`;
-   `dashboard.blade.php`;
-   `profile/edit.blade.php`;
-   las rutas `dashboard` y `profile.*`.

Esta subfase forma parte de **S1 --- Saneamiento del repositorio**.

## 3. Situación inicial

La revisión detectó dos mecanismos de layout coexistiendo.

`dashboard.blade.php` utilizaba el patrón Blade tradicional:

``` blade
@extends('layouts.app')
```

mientras que:

``` text
profile/edit.blade.php
```

utilizaba el componente:

``` blade
<x-app-layout>
```

A su vez, `AppLayout.php` renderizaba:

``` php
return view('layouts.app');
```

pero `layouts/app.blade.php` estaba estructurado mediante:

``` blade
@yield('content')
```

y no mediante `$slot`.

Esto producía una incompatibilidad arquitectónica entre el componente
Blade y el layout que debía renderizarlo.

------------------------------------------------------------------------

## 4. Hallazgo sobre navigation.blade.php

La búsqueda inicial de referencias a:

``` text
layouts.navigation
```

no produjo resultados.

Por tanto, `navigation.blade.php` existía físicamente, pero no estaba
siendo consumido por el layout activo.

Sin embargo, su contenido seguía siendo válido porque utilizaba
navegación genérica:

``` text
Dashboard
Profile
Logout
```

sin dependencias del dominio funcional retirado.

La decisión fue conservarlo y reconectarlo al layout canónico.

------------------------------------------------------------------------

## 5. Decisión arquitectónica

Se decidió utilizar **un solo mecanismo de layout**:

``` text
Componentes Blade / Breeze
```

El patrón canónico queda:

``` text
<x-app-layout>
        │
        ▼
AppLayout.php
        │
        ▼
layouts/app.blade.php
        ├── layouts.navigation
        ├── $header
        └── $slot
```

Se elimina así la coexistencia entre:

``` text
@extends / @section / @yield
```

y:

``` text
<x-app-layout> / $slot
```

para las vistas base conservadas.

------------------------------------------------------------------------

## 6. Normalización de layouts/app.blade.php

`layouts/app.blade.php` fue adaptado para funcionar como vista del
componente `AppLayout`.

La estructura canónica utiliza:

``` blade
@include('layouts.navigation')
```

para navegación y:

``` blade
@isset($header)
    ...
    {{ $header }}
@endisset
```

para encabezados opcionales.

El contenido principal se representa mediante:

``` blade
{{ $slot }}
```

Esto hace compatible el layout con las vistas que utilizan:

``` blade
<x-app-layout>
```

------------------------------------------------------------------------

## 7. Normalización del dashboard

`dashboard.blade.php` dejó de utilizar:

``` blade
@extends('layouts.app')
```

y fue migrado al patrón:

``` blade
<x-app-layout>
```

También utiliza el slot:

``` blade
<x-slot name="header">
```

De esta manera, dashboard y perfil comparten el mismo mecanismo de
layout.

------------------------------------------------------------------------

## 8. Perfil

`profile/edit.blade.php` ya utilizaba:

``` blade
<x-app-layout>
```

por lo que no fue necesario introducir un segundo mecanismo de
presentación.

Con la normalización de `layouts/app.blade.php`, el perfil queda
alineado con:

``` text
AppLayout.php
layouts/app.blade.php
layouts/navigation.blade.php
```

------------------------------------------------------------------------

## 9. Validación de mecanismo único

Se ejecutó la búsqueda de:

``` powershell
Get-ChildItem .\resources\views -Recurse -File |
Select-String -SimpleMatch "@extends('layouts.app')" |
Select-Object Path, LineNumber, Line
```

Resultado:

``` text
0 coincidencias
```

Posteriormente se buscó:

``` powershell
Get-ChildItem .\resources\views -Recurse -File |
Select-String -SimpleMatch "<x-app-layout" |
Select-Object Path, LineNumber, Line
```

Resultado:

``` text
resources/views/dashboard.blade.php
resources/views/profile/edit.blade.php
```

Esto confirma que las dos vistas principales conservadas utilizan el
mismo mecanismo.

------------------------------------------------------------------------

## 10. Validación de navegación

Se ejecutó:

``` powershell
Get-ChildItem .\resources\views,.\app -Recurse -File |
Select-String -Pattern "layouts\.navigation" |
Select-Object Path, LineNumber, Line
```

La búsqueda confirmó la referencia desde:

``` text
resources/views/layouts/app.blade.php
```

mediante:

``` blade
@include('layouts.navigation')
```

Por tanto, `navigation.blade.php` ya no está huérfano.

## 17. Elementos descartados

No se conserva como mecanismo canónico para estas vistas:

``` text
@extends('layouts.app')
@section(...)
@yield('content')
```

Tampoco se reincorporan:

-   layouts administrativos heredados;
-   sidebars por rol;
-   dashboards por rol;
-   navegación de módulos de dominio eliminados;
-   rutas de usuarios heredadas;
-   componentes de CAC, sembradores, cultivos, cosechas, territorios o
    tianguis.
